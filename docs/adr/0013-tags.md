# ADR-0013: Ledger-scoped tags with denormalized storage and configurable exclusivity

Status: **Accepted**

## Context

Users need to label ledger rows (starting with transactions) with a
hierarchical, user-defined vocabulary — cost centres, projects, campaigns,
whatever the domain calls for. The kernel must stay domain-agnostic, so the
vocabulary itself has to be data, not code.

Four decisions were open: where tag definitions live, how assignments are
stored, whether sibling tags are mutually exclusive, and whether tagging a
posted transaction violates ADR-0001.

## Decision

**1. Tag configs are scoped to a ledger.** `TagConfig` carries a `ledger` FK.
There is no global registry and no organization/facility hierarchy above the
ledger — RBAC is already flat and ledger-scoped (ADR-0004), and a tag
vocabulary that outlived its ledger would need an ownership model we
deliberately do not have. A config from ledger A is invisible to ledger B.

Each config declares the `resource` it may be applied to, so a queryable tag
tree can serve several taggable models without cross-contamination.

**2. Assignments are stored denormalized as an ArrayField of ids** on the
tagged row, contributed by the abstract `TaggableMixin` — not via an M2M
through-table.

- *For:* reading a row's tags is free (no join, no extra query in list
  serialization); filtering is a single array `overlap`/`contains` lookup that
  a GIN index serves directly; any model becomes taggable by inheriting one
  mixin and running one migration.
- *Against:* **no per-assignment audit trail.** A through-table row could carry
  `created_by`/`created_date` for each individual tag application; an array
  element cannot. We accept this: tags are mutable presentation metadata, and
  the accounting record they annotate already has its own immutable history.
  If an audit trail is ever required, it arrives as a separate append-only
  event log, not by reshaping storage.

**3. Exclusivity is configurable, not hardcoded.** A boolean
`exclusive_children` on a **parent** config means at most one tag from that
parent's subtree may be applied to a row; a second one is rejected with a
validation error naming the governing parent and the conflicting tag. When it
is false, siblings coexist.

The rejected alternative was a hardcoded rule — either "siblings are always
exclusive" or "never". Both are wrong for some vocabulary: a `Status` tree
wants exclusivity, a `Topics` tree does not, and both plausibly live in the
same ledger. Making it a per-node flag costs one boolean column and one
ancestor lookup on apply, and removes the need for domains to model the
distinction themselves.

**4. Tags are settable on posted transactions.** ADR-0001 makes the posted
accounting record immutable: entries, amounts, accounts, occurrence. Tags are
none of those — they carry no quantity, participate in no balance, and
changing them cannot alter conservation. `Transaction.ALLOWED_POSTED_TRANSITIONS`
therefore includes `tags`, and the behaviour is pinned by an explicit test.
Forcing a reversal transaction to re-label a row would be pure ceremony.

## Consequences

- `TagConfig` maintains hierarchy caches (`level_cache`, `parent_cache`,
  `root_tag_config`, `has_children`) on create, plus a `cached_parent_json`
  ancestry blob with a 15-day expiry for cheap read rendering.
- Tag mutation goes exclusively through `LedgerTagManager`, which enforces
  ledger scope, resource match, duplicate/absent checks, exclusivity, and the
  `tag__apply` permission via `AuthorizationController`.
- `TaggableMixin`, the tag manager and the resource enum are exported on the
  frozen plug surface (`docs/domains/public-api.md`), so plugs can make their
  own models taggable without forking core.
- Renaming or deleting a tag config does not rewrite tagged rows; a soft-deleted
  config simply stops resolving.
